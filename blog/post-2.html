What I learned debugging an I²C bus

The first time a sensor fails to respond, it can feel like a software problem. In practice, it is often a physical one: pull-ups, bus length, or power stability.

Start with the basics

I had the board powered, the code compiling, and the sensor addresses printed to the console. Still, the bus kept failing intermittently. The actual issue turned out to be a weak pull-up network combined with a long trace.

The fix was simple but important

I checked the logic analyzer, verified the timing, and then measured the voltage at the rails. A small change in the resistor values improved the rise time enough to make the entire bus stable.

  • Confirm that the slave has a valid device address.
  • Measure the SDA and SCL lines with a scope.
  • Check for unstable ground return paths.
  • Verify pull-up strength against the bus capacitance.

Why this matters

The best debugging habit is to stop assuming the code is wrong before verifying the electrical layer. Once the signal integrity is clean, the firmware issues are much easier to isolate.
